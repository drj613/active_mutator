# 0.7.0: Run Diagnostics, Memory Ceiling, Clean Aborts

**Status:** draft for DJ's review. Nothing built yet.

**Goal:** When a CI run dies, the log should say which phase it was in, which
mutants were running, and how big the processes were. When the gem can see
trouble coming, it should stop on its own with a partial score instead of
getting SIGKILLed.

**Why:** motion1's `mutation_test` job on the 7 GB runner kept dying with
"The runner has received a shutdown signal" (exit 143) and no score.
motion1 found the cause with two throwaway scripts (b39b8467, reverted in
9b0091b5): a `--require` file that prepended onto `Scheduler`'s private
`spawn`/`finish`, and a shell loop sampling memory every 5s. Both were
fragile. The private-method patch breaks on any gem bump, and `--require`
turns off the gem's own Rails boot, so the file had to re-do it.

**What the failing 0.6.0 run actually shows** (job 107228501245, the
`ps` samples). Two processes blew up, one after the other:

1. 14:34:54–14:41:45: the baseline child (`rspec`, PID 4807, parent 4754)
   grows from 250 MB to 3.7 GB over the 6m50s suite. The parent sits at
   226 MB.
2. 14:41:45: the suite prints `3362 examples, 0 failures` and the child
   exits.
3. 14:41:48–14:42:00: the parent (`active_mutator`, PID 4754) goes from
   226 MB to 6.6 GB in about 12 seconds. It stays at 5.7–7.2 GB until the
   runner is killed at 14:45:38. No mutant ever starts.

So the child built a huge coverage file (#49's gem-file records) and the
parent choked reading it back. After the child exits, 0.6.0's parent parses
the whole `coverage.json` three times: `verify_complete!`, `stamp_digests`,
then `CoverageMap.load`. Other paths parse it up to seven times. 0.6.1 made
the file small, which is why the next run passed, but the repeat parses are
still there. This release fixes them too (see "Reading coverage.json once").

Two lessons for the design:

- "The gem's own memory" means three kinds of process: the parent, each
  worker, and the baseline child. Either side alone would have told half
  the story.
- The phase that killed the run was "parent loading the map", which sits
  inside `Baseline#coverage_map`. It needs its own marker, split from
  "child running the suite".

---

## Scope

In:

1. Phase markers with timestamps: `boot`, `planning`, `baseline` (child
   running the suite), `coverage_load` (parent reading the map back;
   the event carries the file's size in bytes and its example count),
   `mutating`, `escalating` (phase-2 class-body reruns spawn their own
   scheduler, so they get their own phase), `reporting`.
2. Per-mutant `start` and `end` events: sequence number, pid, lane, budget,
   subject, `file:line`, description, then status, seconds, and the worker's
   peak RSS.
3. Memory samples on an interval and at every phase boundary: parent,
   live workers, baseline child.
4. `--max-rss`: warn at 90%, abort cleanly at 100% with a partial score.
5. SIGINT/SIGTERM in any phase: kill children, print the in-flight mutants
   and a partial score, exit 130/143.
6. Best-effort Linux system fields in the memory sample (see the last
   section).

Out: disk usage, other processes' RSS, dmesg OOM lines. Those stay in the
CI job.

## How it hangs together

A small internal event bus, `ActiveMutator::Events`. `Runner` owns it and
passes it to `Scheduler` and `Baseline`. Producers call
`events.emit(:mutant_start, **fields)`; listeners get a frozen `Event`
(`type`, `at` wall time, `elapsed` monotonic seconds since boot, `fields`).
With no listeners it's a no-op, so the default run pays nothing.

- `Scheduler` gets an `events:` keyword (default: a null bus) and emits
  `mutant_start` right after `fork` returns the pid and `mutant_end` in
  `finish` and on the timeout branch of `reap`. This replaces motion1's
  prepend.
- `Runner#call` emits `phase_start`/`phase_end` around each step.
- `Baseline` switches from `system` to `Process.spawn` + a `waitpid` poll
  loop, so the parent knows the child's pid, can sample it, and can kill it
  on a ceiling breach or a signal. Same env, same `out: :err`.
- A sampler thread in the parent ticks every `--sample-interval` seconds
  (default 5) and emits `memory` events. It only reads files and emits, so
  forks from the main thread stay safe (a fork copies only the calling
  thread). Its tick method is public and takes injected probes, so specs
  call it directly instead of sleeping.
- The worker adds its own peak RSS (`VmHWM` from `/proc/self/status`) to the
  JSON payload it already writes. That's the only reliable peak for a
  process that exits between samples. Non-Linux sends nil.

### Reading memory

`MemoryProbe`, one module with injectable roots for tests:

| Platform | Per-process | Notes |
|---|---|---|
| Linux | `/proc/<pid>/status` VmRSS, VmHWM; `/proc/<pid>/smaps_rollup` Pss | plain file reads |
| macOS | `ps -o rss= -p <pids>` once per tick | one subprocess per sample; fine at 5s |
| other | nil | diagnostics still print, memory fields blank |

Workers are forks, so they share copy-on-write pages with the parent. Adding
up RSS counts those pages several times. The ceiling uses the sum of **Pss**
on Linux, which splits shared pages fairly. On macOS it falls back to the RSS
sum, which overcounts and so trips early (the safe direction). The docs will
say so.

Ruby core has no `getrusage`, so it's not an option without Fiddle. Not worth
the dependency.

### The abort path (signals and the ceiling share it)

Today the `Scheduler` trap kills workers and calls `exit(130)` from inside
the handler, for both INT and TERM. New behavior:

1. `Runner` installs INT/TERM traps at the very start of `#call` (so boot,
   planning, and baseline are covered, not just mutating) and restores the
   host's traps on the way out, like `Scheduler#restore_traps` does now.
2. The trap only records the reason. No I/O in the handler: a Mutex there
   raises `ThreadError`.
3. The main loop checks the flag. `run_pool` already polls every 20 ms, and
   the new baseline wait loop polls too. On a flag it SIGKILLs every running
   process group, notes which mutants were in flight, and raises
   `ActiveMutator::Aborted` carrying the finished results, the in-flight
   list, and the reason.
4. `Runner` catches `Aborted`, emits `abort`, calls the reporter's summary
   with `aborted:` info, and returns the exit code.

The ceiling breach goes down the same road: the sampler thread sets the same
flag with reason `memory_ceiling`, and the main loop does the rest.

**Risk to test early (Task 8):** a single huge `JSON.parse` is C code that
may not give up Ruby's global lock for its whole run. If so, the sampler
thread and the signal traps both stall until it returns, which is exactly
the 0.6.0 failure. That's why the `coverage_load` phase event logs the file
size *before* parsing, so the log points at the cause even if nothing runs
after it. If the stall is real, add a size check before the parse: warn
when the file is large compared to `--max-rss`, and abort if parsing it
would plainly blow the ceiling.

An aborted run never passes. `--fail-at` does not apply.

| Reason | Exit |
|---|---|
| SIGINT | 130 (unchanged) |
| SIGTERM | 143 (was 130) |
| memory ceiling | 3 (new) |

The GitHub runner gives only a few seconds between SIGTERM and SIGKILL, so
the abort path must not wait on workers. It kills and moves on. An OOM kill
or a VM teardown is plain SIGKILL, which can't be trapped; for those, the
per-line stderr events are what survives, and `--max-rss` exists to act
before that point.

## CLI flags and config keys

| Flag | Config key | Default | Meaning |
|---|---|---|---|
| `--diagnostics` | `diagnostics: true` | off | human-readable phase, mutant, and memory lines on stderr |
| `--events FILE` | `events_file` | none | the same events as NDJSON, one object per line, flushed per line |
| `--sample-interval S` | `sample_interval` | 5 | seconds between memory samples; only runs when one of the above or `--max-rss` is set |
| `--max-rss SIZE` | `max_rss` | none | ceiling on total gem memory (Pss sum on Linux). Takes `6G`, `6144M`, or plain MB. Warns once at 90%, aborts at 100% |

Signal handling has no flag. It's always on.

`--diagnostics` and `--events` also stop depending on `--require`, so a host
no longer loses the gem's auto-boot to get them. (Separate from this
release: `--require` still turns off the auto-boot, which surprised motion1.
That's worth its own issue, not a change here.)

## What goes where

stdout belongs to the reporter (`--format json` must stay parseable), so every
diagnostic line goes to **stderr**, same as the baseline's progress output and
existing warnings. motion1 pipes only stdout to `tee`, so
`bin/check_mutation_plan` never sees these lines.

**stderr text (`--diagnostics`), any format.** Same shape as motion1's
lines, so the log reads the same:

```
[active_mutator 14:02:11 +3.4s] phase baseline start
[active_mutator 14:03:40 +92.1s] mem parent=1.6G baseline=2.1G avail=3.0G swap=0 psi=0.3
[active_mutator 14:03:52 +104.0s] mutant start #12 pid=4242 parallel Foo#bar app/models/foo.rb:10 replace > with >=
[active_mutator 14:03:54 +105.8s] mutant end #12 killed 1.8s peak=812M
[active_mutator 14:09:10 +423.0s] warn memory at 91% of --max-rss 6.0G (5.5G)
[active_mutator 14:09:15 +428.1s] abort memory_ceiling; in flight: #301 Foo#baz app/models/foo.rb:40, #302 ...
```

In terminal format these interleave with the progress dots on stdout. That's
acceptable for an opt-in debug flag.

**NDJSON (`--events FILE`).** The public, versioned contract. Every line:
`{"v":1,"event":"...","t":"2026-09-23T14:02:11.123Z","elapsed":3.41, ...}`.
Events: `phase_start`, `phase_end` (`phase`), `mutant_start` (`seq`, `pid`,
`lane`, `budget`, `examples`, `subject`, `file`, `line`, `description`),
`mutant_end` (`seq`, `pid`, `status`, `seconds`, `peak_rss_kb`), `memory`
(`parent`, `workers: [{pid, seq, rss_kb, pss_kb}]`, `baseline`,
`total_pss_kb`, `system: {...}` or null), `memory_warning`, `abort`
(`reason`, `in_flight`, `counts`, `score`). New fields may be added under
`v: 1`; renames or removals bump `v`.

**Reporters on a normal run.** `json` results gain `seconds` and
`peak_rss_kb` per mutant. It's additive and cheap, and it's useful without
any flag. Other formats unchanged.

**Reporters on an aborted run.** `summary` gets a new
`aborted: nil | {reason:, in_flight:}` keyword. Custom reporters must accept
it, same as `empty_plan:` in 0.6.0.

- terminal: the usual count block, then `Run aborted (SIGTERM): partial results`,
  the in-flight list, and `Partial mutation score: 71.3% (412 of 764 mutants)`.
  It is **not** labeled `Mutation score:`, so scrapers can't mistake it for a
  finished run.
- github: the terminal output, plus one
  `::error title=Mutation run aborted::` annotation naming the reason, the
  in-flight mutants, and the partial score. Survivor annotations for the
  mutants that did finish still print.
- json: normal object, `"complete": false`, `exit_reason` of `interrupted` or
  `memory_ceiling`, `"in_flight": [...]`, and `score` set to the partial score.
  A complete run gets `"complete": true`.
- stryker-json: writes the report for the finished mutants; in-flight ones
  are left out (the schema has no "didn't finish" status that wouldn't skew
  the score).

## Runner-wide metrics

Worth adding on Linux, inside the `memory` sample when diagnostics are on.
Each is a single cheap file read, and together they explain a kill better
than the gem's own numbers do:

- `MemAvailable`, `SwapTotal`/`SwapFree` from `/proc/meminfo`
- `some avg10` from `/proc/pressure/memory`. The file is missing on older
  kernels and some containers; then the field is null.
- load average from `/proc/loadavg`

These stay the CI job's job:

- **Disk for `/` and `/tmp`**: Ruby core has no `statvfs`, so it means
  shelling out to `df`, and the gem doesn't write enough to matter.
- **Top processes by RSS**: means scanning every `/proc/<pid>`. That's other
  people's processes and not the gem's business.
- **dmesg OOM lines**: often needs root and is blocked in containers.

So motion1 can drop its Ruby file entirely and shrink `sample_resources.sh`
to disk, top-5, and dmesg, or drop it too.

## Reading coverage.json once

A memory fix, not a diagnostic, but it's the fix for the parent's half of
the 0.6.0 failure, so it ships here too.

Each item below is one `JSON.parse(File.read(@out_path))` of the full file:

| Path | Parses today |
|---|---|
| cache fresh | `CoverageMap.load`, `stored_spec_paths` = **2** |
| partial refresh | `load`, `stored_spec_paths` ×2, `stored_digests`, `merge_partial!`, `stamp_digests`, `load` = **7** |
| full rebuild, no cache | `verify_complete!`, `stamp_digests`, `load` = **3** |
| full rebuild, stale cache | 3–4 on the old file, then 3 on the new = **up to 7** |

Worse, the old `map` built at the top of `Baseline#coverage_map` (records
plus its inverted index) stays referenced for the whole method. So on a
stale-cache rebuild it sits in memory while the child runs and while the new
file is parsed.

The change:

1. **`CoverageMap` keeps what `Baseline` re-reads.** Add `spec_paths`
   (defaulting to `["spec"]`, the pre-0.4.0 rule `stored_spec_paths` has now)
   and a `digests` reader. `stored_spec_paths` and `stored_digests` go away;
   `Baseline` asks the map.
2. **Parse once after the child writes.** `run_baseline!` reads the file
   once into `data`, runs the completeness check on `data`, stamps digests
   and spec paths into `data`, writes it with one `AtomicFile.write`, and
   returns `CoverageMap.new(data)`. `verify_complete!` takes a hash instead
   of a path. `stamp_digests` takes `data` and stops reading the file.
3. **Partial refresh merges the hash already in hand.** Read the cache once
   at the top as `data`; `merge_partial!` edits that hash (it only parses the
   small `partial.json`), stamps it, writes once, and builds the new map from
   it. `CoverageMap#initialize` shares `data["records"]` rather than copying
   it, so nothing may read the old map once the merge starts editing. The
   merge runs after the refresh decision, so that already holds.
4. **Drop the old map before a full rebuild** (`map = nil` before
   `run_baseline!`), so GC can free it while the child runs.

On-disk format doesn't change. Existing caches stay valid.

Not in scope: the inverted index (`CoverageMap#build_map`) keys every hit as
a `"path:line"` string, which is likely the biggest memory cost once the file
is parsed. Shrinking it is a bigger change. Measure it with this release's
diagnostics first. Streaming the JSON parse isn't worth a dependency until
the numbers say so.

## Tasks

Each task is TDD, `bundle exec rspec` green, and the self-mutation gate
(`bundle exec exe/active_mutator lib --changed`) exits 0 before its last
commit. Small commits.

Tasks 0a–0d come first. Task 7 changes how the baseline child starts, so
it's easier to land after the parse paths are simpler.

0a. **`CoverageMap#spec_paths` and `#digests`**, with the pre-0.4.0 default.
    Switch `Baseline` over and delete `stored_spec_paths`/`stored_digests`.
0b. **One parse on the full-rebuild path** (`run_baseline!`,
    `verify_complete!`, `stamp_digests`), plus `map = nil` before the child
    runs.
0c. **One parse on the partial path** (`run_partial!`, `merge_partial!`).
0d. **A spec that counts parses**: stub `JSON.parse` for the cache path and
    assert one call per path (fresh, partial, full, full-over-stale), so a
    later change can't quietly bring the repeats back.
1. **Event bus.** `Events`, `Event`, null bus, clock injection. Specs only.
2. **Scheduler events.** `events:` keyword; `mutant_start`/`mutant_end` with
   pid, seq, lane, budget, seconds; timeout branch emits too. Worker adds
   `peak_rss_kb` to its payload (nil off Linux) and `Result` carries
   `seconds` and `peak_rss_kb`.
3. **Phase events in Runner**, including `escalating`.
4. **stderr text sink + `--diagnostics`** (CLI, config key, README row).
5. **NDJSON sink + `--events FILE`**, schema doc in
   `docs/guides/diagnostics.md`.
6. **`MemoryProbe`**: Linux status/smaps_rollup/meminfo/PSI/loadavg with an
   injectable proc root, macOS `ps` fallback, nil elsewhere. Fixture files
   under `spec/fixtures/proc/`.
7. **Baseline via `Process.spawn`** with a poll loop and an exposed child pid.
   No behavior change on its own.
8. **Sampler thread + `--sample-interval`**, samples at phase boundaries too.
9. **Abort path**: Runner-level traps, flag-and-poll, `Aborted`, kill in
   every phase, exit 130/143. Replaces the Scheduler trap. Tested by sending

10. **Reporter `aborted:` support** in all four reporters, plus `complete`,

11. **`--max-rss`**: size parsing, 90% warning, abort with exit 3, baseline

12. **Docs and changelog**: README flags table and an exit-code table, the

## Version

**0.7.0.** New flags and a new event contract, plus two small behavior changes
(SIGTERM exits 143 instead of 130; custom reporters need `aborted:`). The
coverage.json fix and the `--since` deletion work already in `[Unreleased]`
ship with it. No 0.6.2.

## Decided (DJ, 2026-09-23)

1. **No Ruby-level hook API.** The bus stays internal; the NDJSON file is
   the public contract. An `--observer FILE` can come later if someone
   needs it.
2. **`--max-rss` only.** No `MemAvailable` floor until motion1 shows it
   needs one.
3. **Exit 3 for the ceiling**, so CI can tell "ran out of memory" apart
   from "tests too weak".
4. **The coverage.json fix ships in 0.7.0**, not a separate 0.6.2.
